## Summary verdict

The core is solid. RLS is enabled and forced on every product and tenant table, services
consistently pick the narrowest `DbScope` and filter explicitly, and the authorizer denies by
default with a sound "unrelated is 404, related is 403" model. Sessions, CSRF, OIDC
(state, nonce, PKCE, exact issuer, azp, asymmetric algorithms only), secrets (AES-GCM with
random nonces and context binding), the webhook SSRF guard, billing webhook signatures and
storage hardening are all done carefully. I found **no Critical or High issue** and **no
cross-tenant data read or write through RLS gaps**.

The real problems are in **authorization semantics**, where a role can do more than its
description says:

- **Product support can promote itself:** the support role can give itself full write
  access to any tenant (F1).
- **Customer admins can probe other products' users:** any tenant owner or admin can check
  installation-wide whether an email has an account, read user names and emails, and add
  users to their tenant without consent, including users of other products (F2).
- **Plain members can send phishing email:** they can send the built-in invitation email to
  any address, with a link of their choosing, from the product's real sender (F6).

A few Low hardening items follow.

## What I checked and found sound

- **RLS** (`data/sql/0001-0005`, `data/database.py`): `axentra_scope_allows` with ENABLE+FORCE
  on all product and tenant tables. Settings are transaction-local (`set_config(..., true)`), so
  nothing leaks through pooled connections. `check_role` refuses superuser/BYPASSRLS. Tenant scope
  sees product-wide rows (`tenant_id IS NULL`) by design, and services filter explicitly.
- **DbScope usage**: platform scope appears only for global tables (users, sessions, login
  states, rate limits, setup tokens), worker claim/lease, billing webhook dedup, audit lookup,
  re-encryption and purges. Every product or tenant query I read carries explicit
  product/tenant predicates. No raw SQL built from user input: dynamic SQL uses whitelisted
  columns (records sort, tenant/product update fields), and records filters use `@>` with Jsonb.
- **Authorizer**: deny by default. Archived products and suspended tenants are reachable by
  platform roles only. API keys and job principals are confined to their product and tenant,
  never hold PLATFORM permissions, and a tenant-bound key gets nothing at product level. Custom
  roles reject platform permissions, and tenant-scoped roles only grant TENANT permissions.
  Role-scope checks apply on assignment. API key creation enforces "only what you hold".
  `PATCH /users/{id}` platform role changes are limited to platform admins, with last-admin
  guards.
- **Route protection**: `check_routes` walks included routers and their dependencies.
  PUBLIC_ROUTES is minimal. `/metrics` returns 404 in production without a token and is
  compared in constant time. Docs are disabled by default in production.
- **Sessions/CSRF/Origin**: 256-bit tokens stored hashed; idle and absolute expiry; disabled
  users rejected. `__Host-` cookies with HttpOnly, SameSite=Lax and Secure on https. Cookie auth
  on unsafe methods requires the per-session CSRF header plus an Origin allow-list. Login and
  setup check Origin. Bearer-token sessions need no CSRF. CORS has no `*` with credentials.
  Security headers are set. X-Forwarded-For is honored only from trusted proxies and walked
  from the right.
- **Setup token**: hashed, single use, TTL, throttled, refused once an admin exists.
- **OIDC**: state hash plus browser-cookie binding (no login CSRF), single-use state
  (DELETE...RETURNING), nonce and verifier encrypted with row context, S256 PKCE, exact
  issuer, aud/azp, asymmetric algorithms only (oct keys skipped), JWKS refresh rate-limited,
  https-only endpoints, no redirects, response size cap. `email_verified is True` is required.
  `return_to` is open-redirect safe (`//`, backslash, control characters and scheme are
  rejected; absolute URLs only on allowed origins).
- **Invitations**: hashed tokens, TTL, email must match the logged-in user's email (users
  cannot change their email), single acceptance.
- **Secrets**: AES-256-GCM, 96-bit random nonce per encryption, AAD = version|kid|context, so
  a ciphertext cannot be moved between rows. Multiple keys with active-first rotation; batched
  CAS re-encryption. Production refuses inline keys. Problem details are redacted; 5xx responses
  are generic.
- **Webhooks**: https only in production, no credentials in URLs, every resolved address
  checked and the connection pinned to the checked IP (defeats DNS rebinding) with SNI and
  certificate verification, no redirects, timeouts, response cap. HMAC over `ts.body`, 300 s
  tolerance, constant-time compare, rotation with a previous secret.
- **Billing**: Stripe-style signature with tolerance and constant-time compare. Event-id
  dedup in both a read check and an insert `ON CONFLICT`. Targets are resolved only through ids
  Axentra stored (never payload metadata). Body size capped. `fake` provider refused in
  production. No card data handled. Checkout redirects limited to allowed origins.
  Plan/subscription changes require `billing:manage` (a product permission, so tenant owners
  cannot self-upgrade).
- **Storage**: storage keys come only from ids. Names are sanitized. Executable, HTML, SVG and
  script files are blocked by declared type, extension and sniffing. Downloads are always
  `attachment`, `nosniff`, sandbox CSP, with a safe served type. Signed tokens use HMAC-SHA256
  with an HKDF purpose key, bound to file, product and tenant, with expiry, length cap and
  uniform 404, and still check product/tenant status and file visibility. Uploads are streamed
  with size and quota enforcement; authorization happens before the body is read.
- **Notify rendering**: a custom `{{ name }}`-only language (no Jinja, no expressions), single
  pass, HTML escaping in HTML bodies, line breaks stripped from subjects, `EmailMessage`
  header validation, and recipient characters restricted.
- **DoS**: global body limit including chunked bodies, multipart part and field budgets,
  pagination clamps, a cron parser with bounded ranges and a 5-year search bound, a 200-char
  cron limit, payload size caps on jobs, records and settings.

## Resolution

All findings are fixed in commit `8e13e82` (branch `wip/secfix`, on top of `537484f`). Every PoC
was ported to `tests/integration/test_security_review.py`, which asserts the fixed behavior; the
original PoCs now fail except `test_F3` (its session is seconds old, which the fix still allows
by design; see F3). The rules are documented in `docs/architecture/SECURITY_MODEL.md`
("Authorization rules" 7-12, "Passwords", "API keys", "Rate limiting").
